TurboSnap v2 Codex Audit

Measured 2026-07-30 against chromatic-cli@0cf966b5 and fixture repo turbosnap-monorepo@4c3afd6. The fixture repo was clean after all probes.

Fixtures ui, ui-webpack, ui-rsbuild, marketing-ui
Verdict Vite and webpack graph coverage hold; two identity gaps remain
Production state v2 still uploads then falls back to v1

Ranked Gaps

P1 - Top-level storybookHash ignores manifest keys

manifest.ts:190 computes the top-level gate from sorted storyFileHashes.values() and storybookFiles.values() only. A path-only structural change can therefore alter the maps the backend needs to compare while leaving the top-level gate unchanged.

Measurement: renamed packages/ui/src/lib/Badge/Badge.stories.tsx to BadgeRenamed.stories.tsx, changed no bytes, rebuilt Vite stats, regenerated the manifest. tsdiff reported the old story key removed and the new key added, both with hash 5d59dfbcb83fc59e, but storybookHash stayed cf35e70d6fd9c00c.

Risk: if the Index treats storybookHash as the documented first gate, it can skip map comparison and miss story/config identity changes. This matters most for auto-title story files, story adds/removes with duplicate bytes, and any future story identity keyed by path.

Suggested fix: include key identity in the top-level hash, or make the backend compare storyFileHashes and storybookFileHashes keys even when the top-level value is stable. Add a structural fixture probe for byte-identical story rename.

P2 - <staticFiles> is path-independent, but static URL identity is path-based

outOfGraphFiles.ts:117 rolls static files through rollUpHash, whose implementation in graph.ts:29 sorts content hashes and drops file paths. That is correct for many module moves, but wrong for static assets served by URL.

Measurement: static-identity-probe.sh ui found asset rename 91eac9c08be42ae6 -> 91eac9c08be42ae6 and a two-asset content swap 1b81fa5a01662064 -> 1b81fa5a01662064; in both cases storybookHash stayed unchanged. Static byte edits, add/delete, symlinked asset target edits, and symlinked directory additions did move the hash.

Suggested fix: roll static files as path-plus-hash pairs, at least for <staticFiles>. Consider whether <storybookConfig> should also include keys for files whose path itself selects behavior.

P2 - v2 cannot yet produce a traced result in production

v2/index.ts:69 uploads hashes and writes the manifest, then v2/index.ts:73 unconditionally returns { status: "fallback" }. This is a deliberate rollout state, not a silent miss, but it means current CLI bail behavior is still v1 behavior plus v2 diagnostics.

Suggested fix: finish the Index contract so determineChangedFiles returns the changed story file set and v2 can return traced when safe.

P3 - Vite compatibility gate is conservative for the patched fixture

builderViteCompatibility.ts:12 gates on @storybook/builder-vite >= 10.6.0-alpha.4. The local patched ui fixture reports 10.6.0-alpha.3, so the production v2 path would fallback unless CHROMATIC_TURBOSNAP_TRUST_BUILDER_STATS is set. The CJS probe rebuilt patched stats and verified a CJS dependency edit recaptured only Button.stories.tsx.

Suggested fix: keep the conservative production gate, but make the fixture/harness opt-in explicit so future audits do not classify the fixture as invalid when its stats are patched.

P3 - Partial story-index loss remains unexercised

v2/index.ts:61 correctly falls back when the manifest has zero story hashes; this protects the current ui-rsbuild fixture. There is still no independent guard for a builder that indexes some, but not all, stories. I did not find such a fixture state in the four measured projects.

Suggested follow-up: add a fixture or synthetic stats test where exactly one story importer edge is dropped and assert either a fallback or a conservative all-story recapture.

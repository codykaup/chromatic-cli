The findings

G1 — new URL('./x', import.meta.url) assets are invisible

P1 live on ui measured

packages/ui/src/lib/PathDerived/PathDerived.tsx:6 does this: 

const logoUrl = new URL('./logo.svg', import.meta.url).href;

logo.svg is a real 4 346-byte first-party file. It is rendered by the story. Vite emits it into the build output as storybook-static/assets/logo-DOxA0yNj.svg, so the browser genuinely fetches those bytes. And it appears nowhere in the manifest: 

in files?                false
attributed?              false      (not storyReachable, not previewSubtree, not storybookGlobals)
in staticFiles?          false
in storybookConfigFiles? false

edit logo.svg, regenerate manifest
=> manifest BYTE-IDENTICAL

The reason is structural, not a bug in any one function: new URL(..., import.meta.url) never becomes a module in preview-stats.json, so it is not in the graph. It is not under configDir. It is not under a staticDir. v2 hashes exactly those three sets, so the file is outside all of them — and because the asset is referenced at runtime rather than imported, PathDerived.tsx's own source bytes do not change when the asset does. There is no hash anywhere in the manifest that moves.

Why this is worth a ticket even though v1 is equally blind

I checked v1 rather than assuming. A changed logo.svg reaches v1's traceName, which calls shouldBail first — isStaticFile does not match (not under a static dir), isStorybookFile does not match (not under .storybook/) — then looks the path up in modulesByName, finds nothing because it is not a module, and returns silently (v1/getDependentStoryFiles.ts:302-309). So this is parity, not a v2 regression.

It is on the list anyway for three reasons. First, this is the class v2 exists to fix — content-hashing every build input is the whole premise, and here it hashes nothing. Second, it is a guaranteed missed snapshot, not a probabilistic one: the emitted asset filename is content-addressed, so the bytes a browser fetches provably change while every hash stays still. Third, and most usefully: the prior audits list "a story that renders a static asset by URL" as the one probe that would make the static-identity consequence observable, and record it as unexercised because no fixture had one. A fixture does have one — it was added for the PathDerived path-sensitivity work — and the answer is negative. That closes a listed gap with a measurement.

Worth noting what the structural audit did and did not ask. It studied new URL(..., import.meta.url) carefully, and correctly concluded that the emitted URL is basename + content hash on both builders. That answered "does the module's path reach the output?". Nobody asked the adjacent question: "are the referenced asset's bytes hashed at all?" They are not.

G2 — nothing checks that the stats file and projectRoot belong together

P1 silently wrong measured

v1 validates this explicitly. checkStorybookBaseDirectory hard-fails the build with INVALID_OPTIONS when no source module in the stats resolves under the configured base directory (lib/checkStorybookBaseDirectory.ts:36-58, called from v1/index.ts:89). v2 folds the same value into projectRoot (turbosnap/index.ts:49-50) and validates nothing.

The gross case is covered — by accident, but covered. Anchoring one package's stats at an unrelated package makes every ./src/... path fail existsSync, so no story is detected and the new noStoryFiles guard fires. Measured: ui's stats anchored at packages/marketing-ui → 0 stories.

The dangerous case is a structurally similar anchor, which is exactly what a monorepo produces. ui and ui-webpack have byte-identical story paths (verified with diff). Anchoring ui's stats at packages/ui-webpack: 

stories detected:    5        (correct anchor: 5)
config files:        3
storybookFiles:      ./.storybook/preview.ts, <storybookGlobals>, <storybookVersion>,
                     <storybookConfig>, <staticFiles>
BAIL SIGNALS:        none — stories > 0 and configFiles > 0

with the sibling's Badge.tsx made to differ:
Badge story hash — wrong anchor:  9b545b4e9226af47
Badge story hash — correct     :  b6b7b86d1cec56fb
=> hashes computed from the WRONG package's bytes, no bail

The output is a complete, well-formed, entirely plausible manifest whose story hashes were read off the wrong package. Every existing guard passes: stories were found, the config directory resolved, static files resolved. The failure is invisible by construction because existsSync answers "a file exists here" and no one asks "is it the file".

This is v2-narrower in the strict sense: v1 refuses to run, v2 produces confident nonsense. Note also that it survives the two guards added since the previous audit — the fix for silent section loss does not help here, because the sections are not empty, just wrong.

A subagent proposed a related but different hypothesis — that a partial base-dir mismatch would under-capture by dropping some files while keeping others. That is refuted: projectRoot is a single anchor, so first-party resolution is all-or-nothing, and the all-fail case lands on noStoryFiles. The sibling case above is the real shape. The ../../node_modules/* paths do survive a wrong anchor, because they resolve to the same absolute path from either package — which is why 32 files still hash even in the gross case.

G3 — --untraced is silently inert in v2

P1 ignored user config

v1 takes --untraced seriously in two places: untrace() removes matching files from the seed list, and from every reason it traverses while walking upward (v1/getDependentStoryFiles.ts:219-227, 242, 345). The consequence is stronger than "skip the file" — an untraced file never propagates to its importers, and a changed untraced file under .storybook/ never even reaches shouldBail, because that is only called from the traced set.

v2 has no untraced input. The file is a graph module, so it is hashed (v2/manifest.ts:369-395) and rolled into every story subtree that reaches it (v2/graph.ts:22-32, 93-108). Its bytes changing moves those story hashes and the Index recaptures.

Direction is v2 wider — safe, in the over-capture direction. It is a P1 anyway because it is a documented, user-facing option that silently stops working, and the reason people reach for it is precisely that they have a noisy generated file that would otherwise recapture the world on every build. For those users v2 does not degrade gracefully; it undoes the thing they configured. Whether v2 should honour it, or refuse to run with it, or document its removal, is a decision — but silently ignoring it is not one of the three.

G4 — v1's dependency fail-safes have no v2 analogue

P2 under-capture

v2's dependency story is deliberate and documented: don't hash package.json or lockfiles, content-hash the installed files that are in the graph instead (v2/outOfGraphFiles.ts:12-15). That is a better mechanism for the ordinary case and I am not reopening it. What it does not carry over is v1's two fail-safes, both of which fire exactly when the ordinary mechanism has no evidence:

  • changedPackageFiles — when lockfile analysis itself fails, v1 falls back to diffing package.json dependency fields and bails (v1/index.ts:44-83, v1/findChangedPackageFiles.ts:91-104). v2 has no fallback: a dependency change it cannot see through installed bytes produces a byte-identical manifest and captures nothing.
  • nodeModulesMissingInStats — when dependencies changed but the stats contain no node_modules module at all, v1 treats that as evidence the stats are incomplete and bails (v1/getDependentStoryFiles.ts:263-272). This is the sharper one, because hashing node_modules graph modules is v2's entire dependency coverage — so the precise condition under which v1 declares the stats untrustworthy is the condition under which v2 silently covers nothing.

Neither is reachable from the harness (v1's own bail audit records both as untestable there), so this is code-decisive rather than measured. The second one is worth a guard on its own terms: "the graph contains zero node_modules modules" is a cheap, self-contained check on v2's side that needs no git diff, and it is the same shape as the noStorybookConfigFiles guard that already shipped.

G5 — decorated stats names drop real files, and v1 defends against it while v2 does not

P2 latent mechanism measured

hashFiles drops any stats name that fails existsSync (v2/manifest.ts:388). Because hashes.has(path) is also the test for "this is a real file" — gating story detection, the catch-all, and every attribution set — a dropped file is hashed into nothing.

v1 handles this deliberately and v2 has no equivalent. v1's normalize strips URL query params, with a comment naming a real-world case: 

const URL_PARAM_REGEX = /(\?.*)/g;
// Trim query params such as `?ngResource` which are sometimes present
return URL_PARAM_REGEX.test(newPath) && !CSF_REGEX.test(newPath)
  ? newPath.replaceAll(URL_PARAM_REGEX, '')
  : newPath;

(v1/getDependentStoryFiles.ts:104-112.) normalizeStatsPath has no such step.

Reachability — not live on any of the ten fixtures

I went looking, and the honest answer is that nothing currently triggers it:

  • Vite strips the query itself. I added import badgeIconUrl from './badge-icon.svg?url' to a real component and rebuilt ui's Storybook. The stats name came out clean: "./src/lib/Badge/badge-icon.svg", and the manifest captured it (in files? true, storyReachable? true). So the patched builder-vite emits no ?-bearing names at all. My initial P0 call was wrong, and this is what corrected it.
  • Webpack's one decorated name is rescued. Across all ten fixtures there is exactly one "real file plus decoration": ../../node_modules/css-loader/dist/cjs.js??ruleSet[1].rules[4].use[1]!./src/lib/PathDerived/styles.module.css. That CSS file is also named cleanly 24 times in the same stats, and moduleFileNames prefers nameForCondition, which is the undecorated absolute path. It is captured (storyReachable). The prior "dangling reasons" work called this name inert — correct verdict, slightly wrong reason: it is rescued, not absent.

One number sharpens the severity, though. nameForCondition — the accidental defence — is present on 349/375 ui-webpack modules, but on zero modules in all four vite packages. On vite, name is the only spelling a module has, so any decoration that ever does appear there is unrecoverable. The current safety is one builder-plugin change away from evaporating, and it would evaporate silently.

G6 — --externals becomes narrower the moment v2 is authoritative

P2 latent

Refuted as a live defect, confirmed as a latent one. I expected this to be v2's worst parity violation and it is not, today. The externals check does not live in v1's tracer at all — it is in gitInfo (tasks/gitInfo.ts:394-405), and on a match it sets changedExternalFiles and clears git.changedFiles. compareChangedFiles sees the missing list first (turbosnap/index.ts:30-35) and returns the same bailed result for both algorithms, so v2 is never invoked. No difference.

The latent problem is real. An externals file — the canonical example being a .scss bundle compiled outside Storybook — is in none of v2's three hashed sets: not a stats module, not under configDir, not under a staticDir. It contributes to no hash. The bail exists today only because the CLI still takes a git diff. The thing that makes v2 attractive is not needing one — and at that point --externals has nothing left to evaluate against and the bail silently disappears. The same reasoning applies to invalidChangedFiles, which is likewise a fail-safe over a diff v2 does not take.

This belongs on the record now rather than at cutover, because it is an argument about what the CLI must keep computing, and that is a design constraint on the switch.

G7 — PREVIEW_CONFIG_PATTERN hardcodes .storybook

P3 over-capture measured

storybookFiles.ts:12 finds the preview config by path match: 

const PREVIEW_CONFIG_PATTERN = /(^|\/)\.storybook\/preview\.[cm]?[jt]sx?$/;

The literal .storybook is baked in, even though configDir is passed into buildManifest a few lines away. Measured with a custom config directory (-c config, synthetic stats naming ./config/preview.ts importing ./config/customTheme.ts): 

storybookFiles keys : [ <storybookGlobals>, <storybookVersion>, <storybookConfig> ]
previewSubtree      : []                                    <-- no keyed preview entry
storybookGlobals    : [ ./config/customTheme.ts, ./config/preview.ts ]
storybookConfigFiles: [ ./config/customTheme.ts, ./config/main.ts, ./config/preview.ts ]

Coverage is intact — the files land in the catch-all and <storybookConfig> covers their bytes — so this is over-capture in the safe direction. What is lost is attribution granularity: a preview-subtree change recaptures everything through the bucket instead of being attributed to the preview entry. Low severity, but it is a hardcoded assumption sitting next to the value that would remove it, and it is the kind of thing that reads as a bug the first time someone with a custom config dir looks at their manifest.

Method notes and what this audit did not cover

  • Traps observed. yarn build re-run after discovering the tree had moved (trap 1) — every measurement above is against 2df56c7c's compiled output. ui's Storybook was rebuilt twice and its baseline stats restored; marketing-ui was read but never rebuilt (trap 4). All fixture edits were reverted and git status verified clean after each (trap 3). Stats names were normalized with the CLI's own paths.ts logic, never compared raw (trap 5). The harness's own derivation divergence — trap 5's new sibling, added to the README last round — is now moot, since commit 4b1bdf2f aligned it.
  • The instrument that found most of this was not a probe script but a systematic diff of v1's consumed context against v2's input struct. Seven of v2's fields against roughly twenty of v1's reads; each omission classified as wider / narrower / no difference and justified from the code. That is where G3, G4 and G6 came from, and it is repeatable as v2's input list grows — worth doing again the next time a field is added.
  • Not covered. The algorithm itself. Cost. rspack. The Index's half of anything. Whether <storybookGlobals> over-capture matters in practice, which still needs a story depending on neither React nor the Storybook runtime. The four pre-algorithm bail reasons, which still need synthetic git history — though I have now established they cannot diverge between v1 and v2, which lowers the value of testing them.
  • Not chased. Whether other ?-forms (?raw, ?inline, ?worker) survive builder-vite's stats plugin. Only ?url was measured end-to-end. They go through the same plugin path, so I expect the same answer, but I did not spend a second rebuild on it.

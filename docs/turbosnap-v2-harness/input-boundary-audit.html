TurboSnap v2 input-boundary audit

Independent pass, 2026-07-31 · chromatic-cli@cody/turbosnap-v2 (499487d0) · fixtures ~/Projects/turbosnap-monorepo@main, clean tree · CLI rebuilt with yarn build before every measurement (trap 1).

Read this first

The two prior audits and the structural probe cover the algorithm: given a stats file, a project root, a config dir and a list of static dirs, does the manifest attribute correctly? They answer yes, comprehensively. This audit deliberately does not re-tread that. It asks the question one layer out: are those four inputs what v2 thinks they are, and what happens when they are not?

That is where the remaining holes are. Every finding below is a case where v2 produces a well-formed, plausible, wrong manifest — or fails the build — without emitting any signal at all. The algorithm is not at fault in any of them; the input derivation and the absence of "I expected to find something and found nothing" guards are.

Method. Behavioural throughout, per Agreed design 6. Nothing is read off a written manifest to establish reachability. Every claim below is either (a) a measured manifest diff, (b) a measured property of a real fixture stats file, or (c) a code path with the citation given and the reachability stated honestly — including where I could not establish it.

The findings

F1 — <staticFiles> is silently absent for every main.* filename except main.ts

P1 under-capture measured

staticDirs reaches v2 as ctx.storybook?.staticDir ?? [] (node-src/lib/turbosnap/index.ts:63). That value is only ever populated by findStaticDirectories, which returns {} unless v7 is true (node-src/lib/getStorybookMetadata.ts:195). And v7 is set true in exactly one place: the AST branch of getStorybookMetadata, which is reached only when require() of the config fails, and which then locates the file with /^main\.[jt]sx?$/ (getStorybookMetadata.ts:243-256).

Two independent consequences fall out of that single v7 flag:

  • a config that requires successfully leaves v7 = false — so it is parsed, and then its staticDirs are thrown away;
  • a config whose filename the regex does not match (.mjs, .cjs) is never found at all.
Measured — real getStorybookMetadata, one temp project per filename

RESULT main.js        staticDir=undefined            builder=undefined
RESULT main.mjs       staticDir=undefined            builder={"name":"unknown","packageVersion":"0"}
RESULT main.cjs       staticDir=undefined            builder={"name":"unknown","packageVersion":"0"}
RESULT main.js (cjs)  staticDir=undefined            builder=undefined
Confirmed again in plain Node — branch selection per filename, no test runner in the way
main.ts   esm  require=FAIL(MODULE_NOT_FOUND)  astRegexMatch=true   => v7=true   staticDirsRead=true
main.js   esm  require=OK                      astRegexMatch=true   => v7=false  staticDirsRead=false
main.js   cjs  require=OK                      astRegexMatch=true   => v7=false  staticDirsRead=false
main.mjs  esm  require=FAIL(MODULE_NOT_FOUND)  astRegexMatch=false  => v7=false  staticDirsRead=false
main.cjs  cjs  require=FAIL(MODULE_NOT_FOUND)  astRegexMatch=false  => v7=false  staticDirsRead=false

main.ts is the only one of the five that works. Note the middle row: an ESM main.js used to fail require() and therefore took the working AST branch. On Node ≥ 22, require(esm) succeeds, so it now takes the v7 = false branch instead. That coverage was lost to a Node runtime upgrade, with no code change and no signal.

Downstream, staticDirs: [] means hashOutOfGraphFiles walks nothing, staticFiles is an empty map, and rollUpOutOfGraphFiles omits the section entirely (outOfGraphFiles.ts:124). The manifest carries no <staticFiles> key at all — indistinguishable from a project that has no static dirs. Every static asset add, edit, delete and rename is invisible.

Why this matters more than the accepted gap it resembles

The map already accepts "staticDirs unresolvable is indistinguishable from no staticDirs, and v1 is equally blind." The parity half of that is correct and I confirmed it: with staticDirectories empty, v1's isStaticFile matches nothing (v1/getDependentStoryFiles.ts:214-215), and traceName then returns silently because a static asset is not a module and namesById.get(undefined) is undefined (:305-308). So this is not an Agreed design 2 violation.

What is new is the trigger. The gap was accepted on the understanding that it fires when staticDirs is unresolvable — an exotic state. It actually fires on an ordinary config filename choice, including the two most common non-TypeScript ones. And it is <staticFiles>' whole reason for existing that is off: that section was built specifically so v2 beats v1 here rather than tying with it.

All ten fixtures use main.ts (verified: packages/*/.storybook/main.*). So 100% of the static-coverage evidence on the record — the four attribution-matrix.sh D-rows, all five static-identity-probe.sh cases, the staticDirs served-URL decision — was gathered under the one filename that resolves static dirs at all.

F2 — an out-of-graph section that resolves to zero files is omitted with no bail and no warning

P1 missing guard highest leverage

listFilesRecursively swallows every failure and returns [] — a missing directory, an unreadable one, a broken symlink (outOfGraphFiles.ts:180-194). That is the right call in isolation and is documented as deliberate. rollUpOutOfGraphFiles then drops any section with no files (:124). Composed, the two mean "I looked and there was nothing there" and "there was nothing to look for" produce byte-identical manifests.

For <staticFiles> that ambiguity is accepted. For <storybookConfig> it should not be:

  • a real Storybook always has a non-empty config directory, so zero files is near-proof of a mis-derived configDir;
  • configDir is ctx.options?.storybookConfigDir ?? ctx.storybook?.configDir ?? '.storybook' (turbosnap/index.ts:62), and the middle term comes only from parsing -c out of the package.json build script (getStorybookMetadata.ts:124-135) — never from main.*;
  • the entire metadata read is best-effort: getStorybookInfo catches everything and returns {} (getStorybookInfo.ts:34-37);
  • so a project with a custom config dir whose metadata parse failed silently hashes a non-existent .storybook, emits no <storybookConfig> entry, and loses main.* and preview.* byte coverage.

There is also a derivation mismatch that produces the same outcome without any parse failure: findStaticDirectories resolves static dirs relative to deps.options.storybookConfigDir ?? '.storybook' (getStorybookMetadata.ts:229,264), while v2 prefers ctx.storybook.configDir from the build script. A build script with -c ./config and no --storybook-config-dir therefore hashes <root>/config for the config section while the static dirs were resolved under .storybook/ — pointing at paths that do not exist, which listFilesRecursively swallows.

This is the highest-leverage fix on the list. A guard that bails when <storybookConfig> resolves to zero files converts F1, F2, F8 and the -c mismatch from four separate silent blind spots into one named, auditable bail — and it is in the safe direction, so it cannot under-capture.

F3 — a BuildUploadHashesFailure response is discarded

P1 contract violation

determineChangedFiles returns result.buildUploadHashes — a union that carries either build (success) or errors (failure) — and never throws on the failure member (v2/api.ts:70-82). The caller discards the return value entirely: await determineChangedFiles(input.graphqlClient, input.buildId, manifest) (v2/index.ts:133). The surrounding try only catches a thrown error, which is a transport failure.

So a server-side rejection is indistinguishable from success: no bail, no named reason, no Sentry event, and indexUnavailable never fires. The CLI⇄Index contract decided on the predecessor map requires the opposite — the three self-inflicted cases (InvalidStoryFileHashes, InvalidUploadHashesBuildStatus, and a response matching neither union member) must capture to Sentry under distinct fingerprints, while network and timeout failures only log. Today all three are silent, and the "neither union member" case is exactly the one the contract singles out as "indistinguishable from success".

Related and worth stating on the record: api.ts still queries turboSnapMechanism and its doc comment still describes the Index writing onlyStoryFiles onto the build. The settled contract renames the field onlyStoryFilesSource and has the Index return its list and write nothing. That drift is expected — consumption is a separate ticket — but the mutation shape is what F4 depends on.

F4 — v2 aims a write mutation at the baseline build

P1 sequencing hazard

buildId: ctx.build.id (turbosnap/index.ts:56), and the comment above it says plainly: "The current mutation writes to the build. Keep targeting the baseline until the settled return-only Index contract lands." At prepare time ctx.build is the baseline / ancestor build, assigned from gitInfo's output (gitInfo.ts:444, from baselineBuilds.sort(...)[0] at :329); it is only overwritten with the real build much later, in snapshot.ts:268.

This is inert today — the deployed mutation returns Boolean and #11644 is unmerged. It stops being inert the moment the Index ships the write. At that point a monitoring-only run, which by contract influences no build, writes onlyStoryFiles and turboSnapStatus onto somebody's ancestor build — corrupting the baseline that later builds compare against, from a code path whose entire premise is that it is observation-only.

The ordering constraint this implies is worth writing down explicitly on the successor map: the target must move to the announced build before or with the Index write landing, and the two cannot be sequenced independently.

F5 — the harness derives v2's inputs differently from production

P1 measurement validity

Every harness script goes through gen.sh → chromatic turbosnap-manifest (bin-src/turbosnapManifest.ts). That subcommand calls buildManifest directly and derives the four inputs itself, and it does so differently from compareChangedFiles:

InputProduction (turbosnap/index.ts)Harness (turbosnapManifest.ts)Effect
main config regex /^main\.[jt]sx?$/ (getStorybookMetadata.ts:245) /^main\.[cm]?[jt]sx?$/ (:128) hides F1 — harness finds main.mjs/main.cjs that production cannot
v7 / parse path require-then-AST; v7 only in the AST branch always passes true (:134) hides F1 — harness never takes the v7 = false branch
build-script flags merges -c and -s from the package.json build script never reads them (:69-96) divergent — hides the -c mismatch in F2
projectRoot resolve(gitRoot, storybook.baseDir), baseDir defaulting to cwd-relative-to-git-root resolve(gitRoot, flags.storybookBaseDir), defaulting to '.' (:67,89) benign here — harness always passes -b

The first two rows are why F1 went unnoticed through two audits: the harness is more capable than production at exactly the step that fails. This does not invalidate the algorithm findings — those are all downstream of the inputs, and the fixtures feed both paths the same values. It does mean no harness result can be read as evidence about input derivation, and the static and config coverage claims need the F1 caveat attached.

F6 — an inner concatenated-module file can be hashed but attributed nowhere

P2 under-capture, latent measured

buildManifest creates a files entry via ensureFile for the concatenation root and for every importer, but the other files inside a concatenated module are added only as dependencies of the root — they never get an entry of their own (manifest.ts:146-154). Meanwhile collectStorybookFiles derives the <storybookGlobals> catch-all by filtering files.keys() (storybookFiles.ts:77-80).

So the catch-all is closed over files, not over hashes. When a concatenated module's root is itself an orphan global, its inner files are in none of the three attribution homes — not story-reachable, not in a preview subtree, not in the bucket — and their hashes are rolled into nothing.

Reachability on real fixtures

Not live. On every webpack and rspack fixture, each inner concatenated file also appears as a reason somewhere, so it picks up a files entry incidentally and lands in the bucket correctly. But the class is one stats shape away — 3 to 5 concatenated modules per fixture already have their root in <storybookGlobals>:

Webpack concatenates node_modules aggressively and the bucket is mostly node_modules, so the two populations overlap by construction; the fixtures are simply too small for one to land in the other.

The same mechanism falsifies a stated invariant

The pruning ticket records that "serialization is closed over files". pruneSyntheticFiles drops a dependency when it is missing from hashes (manifest.ts:342) — not when it is missing from files. A real file with no files entry therefore survives as a dangling reference, which the probe above shows directly (orphanRoot.dependencies names a path that is not a key). Measured danglingDepRefs = 0 across all six concatenating fixtures, so the invariant currently holds — by luck, not by construction. A one-line assertion in manifest.test.ts would pin it.

F7 — ctx.build.id is dereferenced before any try

P2 robustness

compareChangedFiles reads ctx.build.id while assembling v2's input (turbosnap/index.ts:56), outside every guard. ctx.build is assigned conditionally — if (output.build) ctx.build = ... (gitInfo.ts:444) — from baselineBuilds.sort(...)[0], which is undefined for an empty array (:329). In that same branch git.changedFiles is set to [], which is truthy and so passes the if (!ctx.git.changedFiles) return guard at :30, and no bailReason is set. A TypeError there propagates out of compareChangedFiles and tasks/prepare/traceChangedFiles.ts:87-94 rethrows it as "Could not retrieve dependent story files" — failing the build, with v1 never running.

Stated honestly: I could not prove reachability. parentCommits is derived from commits that have builds, so an empty baselineBuilds alongside a non-empty parentCommits requires getBaselineBuilds to filter everything out, which I did not manage to construct. What is certain is the asymmetry: v1 never touches ctx.build, so this is a build-failure mode that exists only because v2 runs, in a phase whose contract says v2 must never fail a build. The guard is two lines.

For completeness, I checked the other candidate: readStatsFile at v2/index.ts:59 is also outside every try, and index.test.ts:85-96 deliberately pins that a v2 stats-read failure fails the build rather than falling back. That one is parity, not a defect — v1 reads the same file just as unguarded at v1/index.ts:87, so the outcome is identical either way, and a missing stats file is a terminal user error by decision. No ticket.

F8 — prebuilt Storybooks lose both out-of-graph sections

P2 under-capture, silent

With --storybook-build-dir and a project.json present, getStorybookInfo short-circuits to getStorybookMetadataFromProjectJson (getStorybookInfo.ts:21-30), which returns only { version, builder } (getPrebuiltStorybookMetadata.ts:46-49). No configDir, no staticDir. So v2 gets configDir = '.storybook' (usually right, silently wrong for a custom config dir) and staticDirs = [] — the F1 outcome, reached by a different route, on what is a very common CI shape.

This is the same missing guard as F2, and F2's fix covers the <storybookConfig> half of it. The <staticFiles> half needs either a static-dir source that survives the prebuilt path or an explicit, recorded acceptance.

Corrections to the record

1. There are ten fixtures, not four — and six have never been audited

Both audits and both maps work from four fixtures (ui, ui-webpack, marketing-ui, ui-rsbuild). The repo has ten: the six Storybook-version variants ui-sb8, ui-sb9, ui-sb8-webpack, ui-sb9-webpack, ui-sb8-rsbuild, ui-sb9-rsbuild are absent from every report. I generated manifests for all ten; the six new ones are structurally sound, which is itself a useful result — it means resolveStorybookVersion's @storybook/core fallback and the Storybook 8 entry-file names in STORIES_ENTRY_FILES both work, neither of which had been exercised.

2. "rspack currently indexes 0 stories" is true of one fixture, not of rspack

The out-of-scope rationale for rspack on both maps rests on this claim. Measured: ui-sb8-rsbuild and ui-sb9-rsbuild each detect 2 story files, produce a complete storyFiles map that matches index.json exactly, and put zero first-party files in the bucket. Only ui-rsbuild detects 0.

So the zero-story failure is specific to that fixture's configuration or version, not to the builder. rspack stays out of scope by decision and I am not reopening it — but the reason recorded for that decision is no longer accurate, and the predecessor's unclaimed "verify/fix rspack story-detection against bare entry names" ticket now has a working control to diff against.

3. marketing-ui has no graph-rolled preview.* entry at all

Nine of ten fixtures carry a ./.storybook/preview.ts key in storybookFiles. marketing-ui carries none — its preview.ts is empty (0 bytes) and never becomes a module, so there is no subtree to roll up. Its bytes are still covered by <storybookConfig>, and files it would have imported would fall into the bucket, so coverage is intact.

The correction is to the framing: preview.*'s "double coverage" is described on the record as load-bearing redundancy, and on the unpatched-vite control it is not redundant at all — <storybookConfig> is carrying it alone. Any future change that narrows the config section needs to know that.

Method notes and what this audit did not cover

  • Traps observed. yarn build was re-run before the first measurement and no harness script was invoked against a stale dist (trap 1). No fixture file was left modified — the src/__probe/ directory used for F6 was created and removed, and git status was verified clean afterwards (trap 3). No raw stats name was compared against a module name without normalizing both sides with the same logic the code uses (trap 5). marketing-ui was read but never rebuilt (trap 4).
  • Synthetic stats are the new instrument here. F6 and the partial-index measurement both use a hand-written preview-stats.json fed through turbosnap-manifest -s against real files on disk. That reaches graph shapes no fixture produces and no rebuild can be coaxed into producing, and it is considerably cheaper than a Storybook rebuild. It is the right tool for the remaining unmeasured guards, and F5 is the caveat that comes with it.
  • Not covered. The algorithm itself, which the prior audits cover. Cost. rspack. The Index's half of anything. Whether <storybookGlobals> over-capture matters in practice, which still needs a story depending on neither React nor the Storybook runtime. A story that renders a static asset by URL, which would make the static-identity consequence observable for the first time. The four pre-algorithm bail reasons, which still need synthetic git history.
  • Not chased. collectTransitiveDependencies is recursive (graph.ts:93-108), so its stack depth is the longest dependency chain in the graph. Fine at 1962 modules; I did not establish where it breaks, and I do not think it is worth establishing until something suggests it matters.

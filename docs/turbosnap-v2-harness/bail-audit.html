Read this first — v2 emits no bail reasons today

node-src/lib/turbosnap/v2/index.ts:56 unconditionally returns { status: 'fallback' } ("Until we want to lean on the v2 output, we always fallback to v1"), and the dispatcher at lib/turbosnap/index.ts:52 then runs v1. So in production every bail reason is produced by gitInfo.ts, tasks/initialize/index.ts, or the v1 path. v2 is a side-effecting shadow run that builds a manifest, uploads hashes, and discards its own verdict.

The turbosnap-manifest harness command bypasses that, so every "v2" column below describes the evidence the v2 manifest would carry if the fallback were removed — not a decision the CLI ships today. That is the right question to audit now, because removing the fallback is the plan.

3. Ranked gaps — these are the ticket candidates

P0

v2 is blind to every Storybook input that is not a module in the builder graph

v2 hashes only what appears in modules[]. Everything else — main.ts, staticDirs content, preview-head.html/preview-body.html, manager.ts, package.json, lockfiles — has no hash and therefore no way to move any entry. v1 bails on all of them. This is not builder-specific and no stats rebuild fixes it.

Measured
main.ts edit on ui, ui-webpack, ui-rsbuild, marketing-ui: storybookHash unchanged, 0 stories, 0 storybookFiles. .storybook/static/mockServiceWorker.js edit on all three packages that have one: identical. v1 bails on every one of these.
Blast radius
If the v2 fallback is removed as-is, config-only commits capture nothing at all.
ACCEPTED GAP

No guard for “a changed dependency traced to nothing”

Downgraded from P0 and closed as an accepted gap on 2026-07-29 — v2 matches v1 here deliberately. The ranking and the proposed signal below were both wrong; the underlying mechanism is real but is a builder-vite defect already fixed at source. Reasoning follows the table.

nodeModulesMissingInStats requires nodeModules.size === 0 — a whole-file completeness check. There is no per-dependency check, and no downstream guard on a traced result with 0 story files: lib/upload.ts:196 reports APPLIED, and tasks/prepare/index.ts:70 treats [] as truthy. Affects v1 and v2 identically.

Measured
nodeModules.size = 30 / 264 / 198 / 24 across the four fixtures, so the existing condition never fires anywhere. trace -d core-js on ui → traced, 0 story files, no bail, 0 traced files; the same bump on ui-webpack → 4 story files. -d typescript on ui → same silent zero.
Caveat
core-js is a babel-injected polyfill that genuinely is not in the vite bundle, so 0 is arguably right there. The transferable finding is that the CLI has no way to distinguish "genuinely not in the bundle" (correct) from "the builder dropped the edge" (the invisible-CJS silent miss) — and emits nothing either way.
Why not a bail
Three separate states produce the same evidence (a dependency name with no files in the stats), and only the third is a defect: A the name has files that trace to no story — already handled, those files sit in <storybookGlobals> and a bump recaptures everything; B1 the name is genuinely not a preview input (eslint, typescript, and core-js under vite) — capturing nothing is correct, and this is the majority, because v1/getDependencies.ts:52 passes dev: true and so every devDependency bump reaches this path; B2 the builder dropped the module entirely — the real silent miss. So the signal this section originally proposed, changedDependencies.length > 0 && tracedFiles.length === 0, is unusable: it fires on every dev-dep bump, which bails far wider than v1 and fails the map's v1-parity bar in the opposite direction. core-js demonstrates B1, not B2 — ui-webpack/.babelrc sets useBuiltIns: "usage", so babel injects 84 core-js modules into webpack's graph while vite injects none. The two builders ship genuinely different code, so their disagreement is correct, and webpack-as-ground-truth does not apply to polyfill-injected packages.
Where B2 lives
Unpatched builder-vite only, via one line: isUserCode drops any id starting with \0, and @rollup/plugin-commonjs rewrites an ESM→CJS import to \0<path>?commonjs-es-import. The fork commit 49cd7635df7 fixes it by unwrapping the proxy before the filter (builder-vite/dist/index.js:1255), which restores both the module and its importer edge. Not addressable from chromatic-cli, and v1 misses it identically, so there is no v1-parity regression to fix.
Also correct
APPLIED with an empty onlyStoryFiles is not a defect. The Index treats an empty list as “no stories changed, capture nothing”, which is the right outcome for a dev-dep-only commit and is what TurboSnap exists to do. Reporting BAILED there would be false.
Rejected
A v2-side completeness check — enumerate installed packages, compare against the manifest, bail when a runtime-looking dependency is wholly absent — was ruled out of scope. It is the same class as the already-rejected iframe.html stats-completeness guard, and strictly worse: that one tests a short closed set, whereas “is this installed package a runtime preview input?” is exactly the B1/B2 question that has no sound answer.
P1

The builder-vite gate fires on stats that are actually fine, and reports nothing when it does

The gate compares a version string, not the stats. A patched or forked builder that emits correct edges is rejected; conversely any future vite defect at a version ≥ 10.6.0-alpha.4 passes. The fallback is log.info only — no bail reason, no Sentry event, no analytics — and because it runs before buildManifest, a gated project uploads no hashes and writes no manifest, so there is no local artifact to diagnose from either.

Measured
getBuilderViteFallbackReason on the two vite fixtures returns "@storybook/builder-vite@10.6.0-alpha.3 is known to drop Vite CJS importer edges" even though that installed copy carries the CJS-edge patch (COMMONJS_PROXY_SUFFIX present at dist/index.js:1221) and its stats demonstrably trace react to all 3 stories.
Asymmetry
rspack returns null — ungated — while measurably producing a far worse graph (0 stories indexed, 201/202 files bucketed).
P1

changedPackageFiles has no v2 counterpart at all

Both v1 paths key off package.json / lockfile diffs. v2 never hashes either file, so a lockfile change that does not alter node_modules content on disk — or a bump of a package absent from the graph — is completely invisible. Four of the nine taxonomy reasons (changedPackageFiles ×2, changedStorybookFiles, changedStaticFiles) lose their producer the moment v2 stops falling back, and the bail vocabulary that ui/messages/warnings/bailFile.ts and tasks/verify/publishBuild.ts:44-61 depend on will need re-mapping.

Measured
0 package.json entries and 0 lockfile entries in all four manifests (39 / 284 / 202 / 36 files).
P2

v2's previewSubtree key exists only if the builder chose to emit the preview module

Same family as react/index.js being bucketed on vite: v2 inherits whatever the transpiler decided to keep. Anything elided — type-only imports, dead code, an empty module — has no hash and no key.

Measured
marketing-ui/.storybook/preview.ts is 0 lines; vite elides it, it is absent from modules[], previewSubtree is empty, and the manifest's storybookFiles keys are only <storybookGlobals> and <storybookVersion>. An edit to it moves nothing while v1 bails.
Honest bound
A commit that adds real content to that file would appear in the same build's stats and create the key, so v2 recovers in that case. The residual miss is narrower: a preview change that leaves the module still fully elided.
P2

A set-but-unreadable stats file has no named reason

missingStatsFile only covers !ctx.fileInfo?.statsPath. A path that is set but missing, truncated or corrupt throws a raw ENOENT/parse error — which v2's generic catch turns into a silent v1 fallback, and v1 surfaces as an error rather than a bail.

Measured
Both algorithms pointed at /nope/stats.json: Error: ENOENT: no such file or directory, open '/nope/stats.json'. No bail reason.
P2

The five pre-algorithm reasons are unexercised and untestable by this harness

noAncestorBuild, rebuild, invalidChangedFiles, changedExternalFiles, unavailable. All are set before either algorithm runs, so v1 and v2 cannot disagree about them — which is why they are not a correctness risk for the v2 rollout. But nothing in the fixture repo covers them, so a regression there would go unnoticed.

The harness README records "v1 recaptures 0 stories; v2 recaptures all 3 via <storybookGlobals>" and concludes "parity cannot justify the vite edge-loss fix — v1 fails this case too." Measured today against the currently installed patched builder (stats built 11:09), v1 recaptures 3/3 for node_modules/react/index.js, verdict parity. That conclusion is stale for a patched builder; it presumably still holds for an unpatched one, which I could not measure.
  • The CAP-4422 shouldBail check-order mis-categorization is fixed. getDependentStoryFiles.ts:284-292 now tests isStaticFile before isStorybookFile, and a static file under .storybook/static is correctly reported as changedStaticFiles.
  • missingStatsFile is a throw, not a bail key, so the taxonomy is 8 producible reasons + 1 backend-supplied, not 9 symmetric ones.
  • The vite bucket contains no first-party files — re-confirmed (27/39, all node_modules), as do webpack (49/284) and marketing-ui (29/36). Established facts hold.

6. Method traps found (candidates for the harness README)

  1. chromatic trace can never emit changedStaticFiles. bin-src/trace.ts never populates ctx.storybook.staticDir, so staticDirectories is [], isStaticFile is always false, and a static file is mis-reported as changedStorybookFiles. Exercise it by calling getDependentStoryFiles directly with staticDir set.
  2. staticDir entries are path.posix.join(baseDir, entry) (getDependentStoryFiles.ts:115), matching findStaticDirectories, which joins them onto the config dir. Pass .storybook/static, not packages/ui/.storybook/static — a repo-relative path silently disables the check instead of failing.
  3. Don't test missingStatsFile by deleting the file. readStatsFile throws raw ENOENT; the bail only covers an unset path.
  4. marketing-ui's .storybook/preview.ts is empty, so that package has no preview storybookFiles key. Any preview probe there reads as a v2 miss unless you know that.
  5. Content-only edits cannot distinguish "permanently invisible" from "would appear once it has content." main.ts is never a module in any build; an empty preview.ts would become one. Both look identical to tsdiff.mjs.
  6. The fixture's builder-vite is patched but still reports 10.6.0-alpha.3, so the production v2 gate fires on every vite fixture. Record getBuilderViteFallbackReason's verdict alongside every vite measurement, or you will describe manifest evidence that production never computes.

7. What could not be measured, and why

  • noAncestorBuild, rebuild, invalidChangedFiles, changedExternalFiles, unavailable — need a real published build with git history and/or a backend response. No build was published.
  • changedPackageFiles Path A — needs a lockfile diff that findChangedDependencies fails to parse; trace refuses manifest inputs.
  • The unpatched-vite invisible-CJS case — the installed builder is patched, and reverting it would have disturbed a shared fixture mid-audit. The established fact is taken as given, and the same guard-absence mechanism was measured independently via -d core-js. Corrected 2026-07-29: that inference was invalid — -d core-js measured the legitimate case (B1), not the defect. So this case has never been observed end-to-end; its existence rests on reading isUserCode plus the pre-patch probe result. Left knowingly unmeasured: the decision is “no guard, match v1”, which is invariant to the result, so measuring would only sharpen a gap we have chosen not to act on at the cost of disturbing a shared fixture. Re-establish it first if this ever becomes actionable — e.g. if the builder-vite gate is changed to trust unpatched builders.
  • Whether the <storybookGlobals> bucket over-captures in a way that matters — all three fixture stories depend on everything in the bucket, so over-capture is unobservable here. A fixture with a story that uses neither React nor the Storybook runtime would be needed.
  • Silent under-hashing (missing hash → empty string in the roll-up) — indistinguishable from an absent file in the written manifest. Would need instrumentation, not a diff.
